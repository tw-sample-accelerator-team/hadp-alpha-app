# Key functional requirements: CGM Actions Tracker (Slice 1)

Sources: `docs/product/prd.md` (PRD v0.1), `docs/product/vision.md`, `docs/product/intent.md`.
Scope is Slice 1 only (PRD §4.1). Items in PRD §4.2 are out of scope. Where an FR uses a PRD §8 proposed default, the FR says so.

Each FR names who acts, the result they can see, and how a tester checks it. "User" means a person PA has granted access to the selected account (PRD §2, FR-11; §8 Q2 default).

| ID | Who | Result | How to check | Source |
| --- | --- | --- | --- | --- |
| FR-1 | A user signed in to PA | Opening Account Level View → Actions Tracker for one account shows that account's name and its actions list, with no sign-in prompt. | Sign in to PA, select one account, open the tab. The account name and list appear; no sign-in page or dialog is shown at any point. | PRD §5 FR-1; §4.1; §3 (0% separate sign-in); §7 (Okta iframe token bridge) |
| FR-2 | A PA user | The Actions Tracker entry appears only when exactly one account is selected and the `CGM_ACTIONS_TRACKER` rollout is enabled for that account's market. | Select 0, 1 and 2 accounts, with rollout on and off for the market. The entry shows only for 1 account with rollout on. | PRD §5 FR-13; §4.1; §8 Q7 |
| FR-3 | A user | Choosing **Create Action** opens a form with title, planned change, account, related project, owner and expected CGM improvement. | Click **Create Action**; each of these six fields (every PRD §4.3 field except Status, which a new action sets to Open, see FR-12) is on the form. | PRD §5 FR-2; §4.3 |
| FR-4 | A user | On the create form, the account is pre-filled with the selected account and cannot be changed. | Open the form; the account shows the selected account and the control is read-only. A create request naming another account is rejected by the API. | PRD §5 FR-2; §4.3 (Account) |
| FR-5 | A user | The related project picker lists only the selected account's projects (`pse__Proj__c`), by name, plus a "No specific project (account-wide)" choice. | For an account with known projects, open the picker; it lists exactly those project names and the account-wide choice, and no project of another account. | PRD §5 FR-3; §4.3 (Related project) |
| FR-6 | A user | The owner picker returns active people matching the typed name or email once at least 2 characters are typed. | Type 1 character: no search results. Type 2+ characters of a known active person's name, then of their email: the person is listed. An inactive person is never listed. | PRD §5 FR-4; §4.3 (Owner) |
| FR-7 | A user | A saved action stores the chosen owner's name, email and employee id. | Create an action with a known owner; read the action back through the API; it holds that person's name, email and employee id. | PRD §5 FR-4; §6 Privacy |
| FR-8 | A user | Saving is refused, with a message next to each wrong field, when a required field (title, planned change, owner, expected improvement) is empty. | Submit with each required field empty in turn; no action is created and a message shows next to that field. | PRD §5 FR-5; §4.3 |
| FR-9 | A user | Saving is refused, with a message next to the field, when the title is over 120 characters or the planned change is over 2,000 characters. | Submit a 121-character title and a 2,001-character planned change; both are refused with field messages. 120 and 2,000 characters save. | PRD §5 FR-5; §4.3 |
| FR-10 | A user | Saving is refused, with a message next to the field, when the expected CGM improvement is outside −100.0 to +100.0 or has more than one decimal place. | Submit −100.1, +100.1 and 1.25; each is refused. −100.0, 0.0 and +100.0 save. | PRD §5 FR-5; §4.3; §8 Q1 default (signed pp delta) |
| FR-11 | A user | Saving is refused when the related project is not one of the selected account's projects. | Send a create request with another account's project id; the API rejects it and no action is created. | PRD §5 FR-5; §4.3 |
| FR-12 | A user | A newly saved action has status Open and appears in the account's list without a page reload. | Save a valid action; the row appears in the list with status Open, and the browser does not reload the page. | PRD §5 FR-6; §4.3 (Status) |
| FR-13 | A user | The list shows every action of the account, account-wide and project-linked, and no action of another account. | Seed an account with one account-wide and one project-linked action, and another account with one action; the list shows exactly the first two. | PRD §5 FR-7; §4.1 |
| FR-14 | A user | Each list row shows title, planned change, related project (or "Account-wide"), owner, signed expected improvement (for example "+1.0 pp"), status and last-updated date. | Seed an action of +1.0 with no project; its row shows all seven items, with "Account-wide" and "+1.0 pp". A −0.5 action shows "−0.5 pp". | PRD §5 FR-7; §4.3 (Expected CGM improvement) |
| FR-15 | A user | List rows are ordered Open, then In Progress, then Implemented, newest first within each group. | Seed two actions of each status with different times; the list order matches the rule. | PRD §5 FR-7 (ordering is a PRD assumption, §4.3 note) |
| FR-16 | A user | When the account has no actions, the tracker shows an empty-state message and a **Create Action** button. | Open the tracker for an account with no actions; the message and button show, and the button opens the create form. | PRD §5 FR-8 |
| FR-17 | A user | The user can change an action's status to any of Open, In Progress or Implemented, and the new status is shown the next time anyone opens the tracker for that account. | Move an action through every pair of statuses (including backwards); after each, a second user opening the tracker sees the new status. | PRD §5 FR-9; §4.1; §8 Q4 default (free moves) |
| FR-18 | A user | Every create and every status change records the actor's employee id and name and the time, and the history is never overwritten. | Create an action, then change its status twice; the stored history has three entries, each with actor id, name and time, and the first entries are unchanged. | PRD §5 FR-10; §6 Auditability (audit trail is a PRD assumption, §4.3 note) |
| FR-19 | A user | Each action shows who created it and when it was last updated. | Create an action as user A, change status as user B; the action shows A as creator and the time of B's change as last updated. | PRD §5 FR-10 |
| FR-20 | A person without PA access to the account | Opening the tracker for that account shows "You don't have access to this account" and no actions. | Sign in as a user PA denies for the account; open the tracker; the message shows and no action data is displayed. | PRD §5 FR-11; §4.1; intent (access follows PA) |
| FR-21 | A caller without PA access to the account | Every API call to list, create or update that account's actions returns 403. | Call each endpoint with a valid token of a user PA denies for the account; each returns 403 and no data changes. | PRD §5 FR-11 |
| FR-22 | A caller without a valid PA Okta token for the environment | The API serves no request. | Call the API with no token, an expired token, a token from another environment's issuer, a wrong audience, and no `emp` claim; each is refused with 401. | PRD §6 Security; §7 (per-environment issuer) |
| FR-23 | A user whose PA session ends or who signs out of PA | The tracker stops making API calls and shows "Session ended, reload Project Accounting". | End the PA session while the tracker is open; the message shows and the network log has no further API calls from the tracker. | PRD §5 FR-12 (PRD assumption, §4.3 note) |

## Not key FRs (kept as architecture characteristics)

PRD §6 scale, performance, availability, data protection, encryption, framing by PA origins only, token storage, accessibility and the 900 px embedding width are architecture characteristics, not FRs. They are left for the architecture characteristics document. FR-22 is kept here because it is a checkable allow/deny result.
